# M6 Routines Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wren notices repeated tasks locally, offers to turn them into
routines, runs them on a schedule or on request ("do my usual") with the
agent, stops on any drift, and always asks before paying; a small
menu-bar agent keeps schedules alive with the window closed.

**Architecture:** a new `routines` crate (no Servo) owns detection
(local job over `store` history and agent timelines), recipes, the
scheduler and run state. Runs use the M4 `agent` with a `TaskSpec`
built from the recipe, preferring the site's WebMCP tools (M4), then
the recorded steps (refs re-resolved by role and name), then agent
reasoning. Confirmation goes through the M4 policy with a routine-level
spending cap. The menu-bar agent is a second tiny binary
(`wren-agent`, no Servo, no GPUI window) registered as a LaunchAgent;
it owns the schedule and wakes or starts Wren when a run is due.

**Tech Stack:** as M5, plus `objc2-app-kit` status item for the menu-bar
agent, `objc2-user-notifications` (macOS notifications with actions),
`chrono` + `cron`-style own schedule parser (no daemon dependency).

**Spec:** `docs/superpowers/specs/2026-11-13-wren-browser-design.md`
(sections 8.2 safety, 8.5 pins as routine output, 8.6, 9, 10 M6).
Roadmap: `docs/superpowers/plans/2026-11-13-roadmap.md`.

## Global Constraints

- All M0 to M5 constraints hold.
- Detection is local only: no history leaves the machine; if a model
  call is used for naming or summarising a candidate it must be a local
  provider (Ollama) or the user's explicit consent per candidate.
- Payment always needs approval by default. A routine may have a
  spending cap (`auto_confirm_below`, currency, default none); above it,
  or with none set, approval is asked via a macOS notification with
  Confirm / Review actions or in-app.
- Drift stops the run and asks: item missing, price change above
  `routines.price_drift_percent` (default 10), layout changed (a
  recorded ref cannot be re-resolved and no WebMCP tool covers the
  step), login required.
- Triggers: schedule, suggestion only, page change (pinned page data
  differs), omnibox "do my usual" (and the routine's own phrase), and
  user-written routines in natural language.
- The menu-bar agent is opt-in (`routines.background_agent = false` by
  default); without it, schedules run only while Wren is open and missed
  runs are offered on next launch, never silently replayed.
- Every run writes an agent timeline (M4) linked to the routine.

## Review Focus

1. **A cart total above the cap, or any total with no cap** must stop
   at checkout and ask; nothing is submitted without the user's tap.
   Pinned by `payment_without_cap_asks` and `over_cap_asks` (Task 3).
2. **A price that moved 15% since the recipe** must stop with a drift
   prompt showing old and new prices. Pinned by `price_drift_stops_run`
   (Task 3).
3. **Detection must not propose a routine from two visits** or from
   private-window history; it needs at least 3 similar occurrences in
   6 weeks. Pinned by `needs_three_occurrences` (Task 1).
4. **The Mac sleeping through a scheduled time** must not run the
   routine later silently: on wake it asks "missed at 08:00, run now?".
   Pinned by `missed_run_is_offered_not_replayed` (Task 4).
5. **Two routines due at the same minute on the same site** must run one
   after the other, not in parallel tabs fighting over one cart. Pinned
   by `same_origin_runs_serialise` (Task 4).

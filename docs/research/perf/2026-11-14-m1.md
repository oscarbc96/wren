# M1 RAM benchmark (2026-11-14)

| Browser | Workload | Phys footprint median (MB) | RSS median (MB) | Runs |
|---|---|---:|---:|---:|
| Wren | tabs10 | 1,179 | 668 | 3 |
| Chrome | tabs10 | 793 | 1,635 | 3 |
| Wren | tabs20 | 2,214 | 1,435 | 3 |
| Chrome | tabs20 | 1,387 | 2,790 | 3 |

Per-run footprints (MB): Wren tabs10 1,201 / 1,169 / 1,179; Chrome tabs10 781 / 793 / 806; Wren tabs20 2,374 / 2,139 / 2,214; Chrome tabs20 1,383 / 1,426 / 1,387. Raw JSON for every run sits next to this file.

Method: `parity ram --browser <wren|chrome> --workload <tabs10|tabs20>` (release build, `WREN_BIN=$CARGO_TARGET_DIR/release/wren`). Each combination run three times, alternating Wren and Chrome, median reported. Live sites are noisy. No other apps started during measurement and no two measurements run at once.

## Comparison and M0

M0 (`docs/research/perf/2026-11-13-m0.md`, 2026-11-13, tabs10): Chrome RSS median 462,733,312 bytes (10 samples, process tree RSS sum only). Wren M0 was pending.

M0 summed only the process tree RSS; M1 and the memory diet work report `phys_footprint` summed over every process of the profile (browser plus content processes), plus RSS for reference. This makes totals not directly comparable to M0 RSS-only figures.

Memory diet baseline (2026-11-14, tabs10, `phys_footprint` over all profile processes): Wren ~830 MB at M0-era measurement context noted in memory diet, relief median 1,193 MB in the part 2 alternating-run table (`docs/research/2026-11-14-memory-diet.md`).

## Gap to target

Spec 11 target: at most 50% of Chrome.

- By `phys_footprint` (the metric the spec now uses), Wren is at 149% of Chrome on tabs10 and 160% on tabs20. The target is not met; the gap is about 3x.
- By RSS, Wren is at 41% (tabs10) and 51% (tabs20) of Chrome. The metrics disagree because footprint counts compressed and swapped dirty memory that RSS leaves out, and Wren's content processes hold far more of it than Chrome's renderers. Why exactly is not yet measured.
- Footprint is the honest number. The largest Wren rows in the memory report are SpiderMonkey heaps and per-process Stylo and font caches in each content process; next levers are listed in `docs/research/2026-11-14-memory-diet.md` (one process per site, tighter tab sleep, cache caps, disabling unused Servo features).

## Regression check

M0 has no Wren figure (the M0 binary could not load pages yet), so there is nothing to regress against. These M1 numbers are the baseline for M2's 10% gate.

## Must-work exit checklist (owner, logged-in profile required)

These require the owner's logged-in profile and were not attempted here.

- **Calendar:** open Google Calendar in Wren and verify the signed-in calendar view is usable. `target/release/wren --profile-dir <owner-profile> https://calendar.google.com/`
- **Slack:** open Slack web in Wren and verify the signed-in workspace is usable. `target/release/wren --profile-dir <owner-profile> https://app.slack.com/`
- **DevTools:** start Wren with remote debugging and connect from Firefox `about:debugging` (Network location `127.0.0.1:6000`). `target/release/wren --devtools 6000 https://example.com` (or `--devtools` for default port per settings)
- **Meet:** use Meet in Wren, or route to Chrome by per-site rule if it is not usable. `target/release/wren --profile-dir <owner-profile> https://meet.google.com/`; to route: add `meet.google.com` to `sites.open_in_chrome` in settings or use "Always open this site in Chrome" from the toolbar menu, then open a Meet link and confirm it opens in Chrome.

# Spike: using Bun (2026-11-14)

Bun is now mostly Rust (about 90% of the repo) on JavaScriptCore, MIT
itself with JavaScriptCore/WebCore under LGPL-2 linked statically. Two
ideas were measured on an M-series Mac, release builds, `parity ram`
tabs10, alternating runs.

## 1. mimalloc (Bun's allocator) for all of Wren

`mimalloc` crate with the `override` feature, so Rust and SpiderMonkey
allocations both go through it (Servo already sets its own Rust global
allocator, so the override is the only way in). Verified active with
`MIMALLOC_VERBOSE=1`.

| Build | tabs10 footprint per run (MB) | median |
|---|---|---:|
| system malloc | 1,160 / 1,289 / 836 | 1,160 |
| mimalloc defaults | 1,305 / 1,305 / 1,010 | 1,305 (+12%) |
| system malloc (second pair) | 1,011 / 1,118 | 1,065 |
| mimalloc, purge delay 0, no eager commit | 1,136 / 1,108 | 1,122 (+5%) |

mimalloc is worse with defaults and no better tuned. Not adopted. The
macOS allocator plus Wren's pressure relief stays.

## 2. Bun as the host for extension background workers (M3)

MV3 service workers have no DOM, which matches what Bun offers (JS plus
web APIs). Idle footprint of a background-shaped script (listeners, a
2,000-entry map, a timer):

| Process | phys_footprint | RSS |
|---|---:|---:|
| Bun 1.4.4 running the script | 5.9 MB | 14 MB |
| Wren content process on `about:blank` | 11 MB | 30 MB |

Bun is about half of an empty Servo content process before any
extension code loads; both grow with the extension's own JS heap.

Not adopted for M3 now:
- M3 already stops backgrounds after 30 s idle, so they rarely sit in
  memory; the saving applies only while one runs.
- It adds a second JS engine and about 60 MB of binary to the bundle,
  and LGPL obligations for the statically linked JavaScriptCore (ship
  Bun unmodified and point to its relink instructions).
- `chrome.*` in background code would need a second bridge (IPC to Bun)
  next to the in-page one.

Revisit if the M3 extension harness shows running backgrounds as a top
RAM cost.
